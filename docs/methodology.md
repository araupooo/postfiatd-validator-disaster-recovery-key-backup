# Methodology

## Pinning

The assessed repository is `postfiatorg/postfiatd`. The pinned commit
`0085a1ff885d6a446369cf73a4430f75af22be55` is the LIVE main HEAD, fetched
via the GitHub API (`GET /repos/postfiatorg/postfiatd/commits/main`) at
build start on 2026-11-27 and re-verified, not carried over from an
earlier pin. The full git tree (1,947 paths) was fetched via the API
(`GET /repos/.../git/trees/<sha>?recursive=1`) and vendored as
`evidence/pinned-tree-paths.txt`.

## Static analysis

The 31 cited files were downloaded verbatim at the pinned commit and
verified against the tree: for each file, the git blob SHA-1
(`SHA-1("blob <len>\0" + content)`) and the byte size must equal the tree
entry. All 31 matched; the result is recorded in
`evidence/pinned-tree-manifest.json` and re-checked by
`scripts/harness/inventory_check.py` (PIN-01) on every harness run.
Line numbers in every citation were read from the vendored copies, never
from memory or from another pack's notes. Where a check's first reading
was wrong, the harness itself caught it: two cases during the build — a
revocation section that is a commented example, not an active section,
and a "recovery" term that also matches secp256k1's signature-recovery
module — were fixed and re-verified by the harness.

## Models

The drills in `scripts/harness/drill.py` are software models of the
pinned rules, not executions of postfiatd:

- Manifests are canonical strings signed with pure-Python secp256k1
  (RFC 6979 deterministic nonces, standard library only). The
  implementation was cross-checked against OpenSSL in both directions at
  build time: OpenSSL verified a Python signature ("Verified OK") and
  Python verified an OpenSSL signature.
- The peer manifest cache applies the pinned rule exactly: sequence not
  strictly greater than cached is stale (`Manifest.cpp` line 411);
  sequence `0xFFFFFFFF` revokes (`Manifest.cpp` line 240).
- Node ID is modelled as the first 20 bytes of SHA-512 over the
  compressed public key. The pinned source only establishes
  `nodeID = calcNodeID(masterKey)` deterministically
  (`ValidatorKeys.cpp` lines 60, 87); the exact hash construction is not
  in the vendored set, so the model states its convention openly. No
  recovery verdict depends on the exact hash — only on determinism (same
  key gives the same ID) and distinctness.
- Lab keys are fixed test secrets derived from SHA-256 of labelled
  strings (`POSTFIAT-DR-LAB-TEST-SEED-...`). They are never real keys and
  are never used outside the models.
- Timings printed by the drills are wall-clock times of the model steps
  on the build machine. They are printed to stdout only (captured in
  `outputs/run_all.log`) and never written to JSON, because they are not
  reproducible byte-for-byte. Runbook "measured" times are these model
  times; operator times are labelled ESTIMATE; sync times are UNTESTABLE.

## Label discipline

Every substantive claim is labelled: **MEASURED** (verified against the
pinned source or produced by executing the harness), **SIMULATED**
(software model of specified behaviour — no live validator involved),
**UNTESTABLE** (would need a live validator host, network access, or
operator/publisher action that was not available), **ANALYSIS**
(interpretation, severity rating, or recommendation). Severity ratings
are ANALYSIS, not measured quantities.

## Reproduction

`scripts/run_all.sh` re-runs the whole harness and prints full SHA-256
digests of every output. `scripts/verify_digests.sh` checks every
deterministic shipped file against `SHA256SUMS`. Two shipped files are
excluded from `SHA256SUMS` by design: `outputs/run_all.log` embeds the
run timestamp and the absolute pack path, so it is not byte-reproducible;
`outputs/reproduction/COMPARISON.md` is written by
`clean_reproduce.sh` after digest verification and is not regenerated by
`run_all.sh`, so a fresh copy has no copy to check. `scripts/clean_reproduce.sh`
reproduces from a fresh copy of the pack alone: it copies the pack to a
temporary directory (excluding generated outputs and local-only files),
re-runs the harness there, verifies digests, compares every regenerated
`outputs/*.json` byte-for-byte against the committed ones, and writes
`outputs/reproduction/COMPARISON.md`. It uses no network, clones no
other repository, runs no Conan, and calls no package manager. See
`outputs/reproduction/COMPARISON.md` for the committed result.
`.github/workflows/reproduce.yml` runs the same check in CI on push, so
the reproduction is CI-attested rather than only self-run.

## Limitations (honest)

- The assessment is of the pinned source tree and the documented
  deployment, not of a live validator host. Host contents, running
  config, actual backup files on operator machines, and GitHub Secrets
  state are UNTESTABLE here.
- No postfiatd binary was built or run. All recovery behaviour is
  modelled; the drills prove the logic of recovery, not its wall-clock
  duration on production hardware.
- Ledger re-sync duration is UNTESTABLE (network-dependent). The
  runbooks' operator times are ESTIMATEs, not measurements.
- The vendored `deploy.yml` is verbatim public source, so it contains
  the same validator host IPs already public in that repository; the
  pack's prose cites the token-by-IP mechanism by line number only and
  lists no IPs. No non-public host information is introduced.
- The task's `validator-keys.json` filename appears throughout as the
  documented master-key file name; no real key material of any kind is
  in the pack (only fixed, labelled test keys in the models).
